# BT04-E BLE GATT 对接约定

## 广播与 GATT

BT04-E 广播名称继续使用 `ESP32-LORA-BRIDGE`。标准固件使用 16 位 UUID，小程序使用 Bluetooth Base UUID 展开的 128 位表示。

| 用途 | UUID | ESP32 属性 |
|---|---|---|
| 主服务 | `0000FFE0-0000-1000-8000-00805F9B34FB` | Primary Service；AT 值 `FFE0` |
| 小程序发命令、BT04-E 接收 | `0000FFE2-0000-1000-8000-00805F9B34FB` | Write；AT 值 `FFE2` |
| BT04-E 发数据、小程序接收 | `0000FFE1-0000-1000-8000-00805F9B34FB` | Notify/Read；AT 值 `FFE1` |

BT04-E 断开后应重新广播。业务帧缓存和串口/LoRa 转发仍由连接 BT04-E UART 的控制器负责。

## 安装前查询与设置

先查询实物模块：

```text
AT+UUID
AT+CHAR
AT+WRITE
```

预期依次返回 `FFE0`、`FFE1`、`FFE2`。如需主动设置：

```text
AT+UUID0xffe0
AT+CHAR0xffe1
AT+WRITE0xffe2
AT+RESET
```

设置后必须重启生效。如果实物模块没有 FFE2，先用 nRF Connect 查看实际 GATT 服务和特征，不要套用猜测值。

## 字节流规则

BLE 仅作为透明字节流，特征值中仍使用现有业务帧：

```text
AA | commandId | payloadLength | payload... | checksum | F9
```

- `payloadLength` 为 0–230。
- `checksum = (commandId + payloadLength + 所有 payload 字节) & 0xFF`。
- 多字节整数使用 Big Endian。
- 小程序当前按最多 20 字节逐块、逐次等待成功后写入 RX。
- 控制器串口接收侧必须累计数据直到得到完整合法帧；一次 BLE Write/UART 接收不等于一帧。
- BT04-E 可能把一帧拆成多次 Notify，也可能连续发送多帧；小程序端会增量解包。
- 遇到错误校验和或错误包尾时，接收端应跳到下一个 `0xAA` 继续同步。

## 小程序会使用的命令

| ID | 方向 | Payload |
|---|---|---|
| `01` | 小程序→设备 | 比赛控制：`00` 停止，`01` 开始，`02` 重置 |
| `02` | 设备→小程序 | 运动员ID(2) + 圈数(1) + 单圈百分秒(3) + 总百分秒(3) + 名次(1) |
| `04` | 设备→小程序 | 全量成绩传输状态：`01` 开始，`00` 结束 |
| `05` | 小程序→设备 | 查询领滑成绩，无 Payload |
| `06` | 设备→小程序 | 领滑运动员ID(2) + 圈数(1) + 总百分秒(3) |
| `07` | 小程序→设备 | 查询比赛状态，无 Payload |
| `08` | 设备→小程序 | 比赛状态(1)：按现有 STM32/Android 约定 |
| `11` | 小程序→设备 | EPC(4) + UTF-8 姓名长度(1) + 姓名字节 |
| `12` | 小程序→设备 | UTF-8 姓名长度(1) + 姓名字节；设备随后等待 RFID 扫描 |
| `15` | 小程序→设备 | 运动员ID(2) |
| `17` | 设备→小程序 | 运动员ID(2) + EPC(4) + UTF-8 姓名长度(1) + 姓名字节 |
| `18` | 小程序→设备 | 查询运动员名单，无 Payload |
| `19` | 设备→小程序 | 名单传输状态：`01` 开始，`00` 结束 |
| `F1` | 设备→小程序 | 沿用现有通用响应定义；首版界面不依赖它推断最终比赛状态 |

## 连接后的顺序

1. 小程序连接并发现主服务及两个特征。
2. 小程序打开 TX Notify。
3. 小程序依次发送 `18`（名单）、`07`（比赛状态）、`05`（领滑成绩）。
4. 比赛页在前台时每秒发送一次 `07` 和 `05`。
5. ESP32 收到 STM32/LoRa 的实时 `02`、`06` 等完整帧后，应立即通过 TX Notify 转发。

## 控制器与 BT04-E 实现建议

- BLE 回调只负责把 RX 字节放入环形缓冲区，协议解析和串口/LoRa 转发放在主循环或独立任务中，避免阻塞 BLE 任务。
- TX Notify 建立发送队列并做拥塞控制；不要在一个回调里无限等待。
- 只有 CCCD 已开启且连接有效时发送 Notify。
- 保留现有串口/LoRa 协议解析；BLE 与经典蓝牙 SPP 可在迁移期同时存在，但同一时间只允许一个控制端发送管理命令。
- 日志至少打印连接、断开、订阅状态、完整帧命令ID、校验失败和队列溢出。

## 联调验收

1. Android 与 iOS 真机都能发现同名设备并完成通知订阅。
2. 连接后名单、比赛状态、领滑成绩能在 3 秒内显示。
3. 开始、停止、重置均以设备返回的 `08` 为准，页面不提前假定成功。
4. 连续添加/删除运动员后重新查询名单一致。
5. 人工制造 20 字节边界、半包和粘包，双方不丢帧且能从坏包恢复。
6. 连续运行至少 30 分钟，逐圈成绩、排名和领滑数据稳定。
7. 关闭手机蓝牙、离开小程序、ESP32 重启后，重新连接并全量同步可恢复。
