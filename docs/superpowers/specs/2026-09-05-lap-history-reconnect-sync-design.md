# 圈历史重连同步设计

## 目标

DetectOnly 固件在单场比赛期间为每名运动员保存最多 100 条有效过线记录。小程序蓝牙重连后，在设备仍处于检测状态且本地存在当前比赛会话时，从固件读取全部圈记录，并以一次事务更新本地实时成绩和比赛历史。

本功能只保存当前比赛的运行期数据。执行 `0x02` 成功后，圈记录与现有临时运动员、成绩、黑名单和去重记录一起清空，不引入 TF 卡、Flash、EEPROM 或数据库持久化。

## 固件数据结构

每条 `AthleteScoreEntry` 继续保存运动员 ID、当前圈数、最近单圈时长和当前总时长，并新增以下字段：

```cpp
static constexpr uint16_t LAP_RECORD_CAPACITY = 100;
static constexpr uint8_t LAP_RECORD_SIZE = 6;

uint8_t lapRecords[LAP_RECORD_CAPACITY][LAP_RECORD_SIZE];
uint16_t lapRecordCount;
```

每条圈记录固定 6 字节，多字节整数使用大端序：

```text
byte0-byte3：单圈时长，uint32，单位百分秒
byte4-byte5：圈号，uint16，范围 1～100
```

50 名运动员的圈数组固定占用 30,000 字节。`lapRecordCount` 表示已使用记录数，不扫描空槽。

成功定义运动员时只建立圈号为 0 的当前成绩，不写入圈记录。之后每次通过 8 秒规则的有效运动员检测，先计算单圈时长和新圈号，再把 6 字节记录写入当前运动员的下一个空槽，最后更新当前成绩并发送现有 `0x12` 实时成绩包。

第 100 圈可以正常保存。已保存 100 条记录后再次检测该运动员时，不改变圈数、最近单圈时长或总时长，不覆盖旧记录；固件返回新增的“圈记录已满”状态，其他运动员和比赛检测继续运行。

## 协议扩展

现有 `0x11`、`0x12`、`0x13` 的格式和含义保持不变。新增三个命令：

```text
0x15：APP 请求全部圈历史
0x16：STM32 返回一个圈历史分片
0x17：STM32 返回圈历史传输状态
```

### `0x15` 请求全部圈历史

发送方为 APP，Payload 长度为 0，只允许在检测中执行。正常响应不额外发送 `0xF0`，而是发送一个完整的 `0x17/0x16/0x17` 序列。

### `0x16` 圈历史分片

发送方为 STM32。Payload 格式如下：

```text
byte0-byte1：运动员 ID，uint16
byte2：分片序号，uint8，从 0 开始
byte3：该运动员的分片总数，uint8，范围 1～3
byte4：本分片记录数，uint8，范围 1～37
byte5...：按圈号升序排列的 6 字节圈记录
```

Payload 长度必须等于 `5 + 记录数 × 6`，最大为 227 字节，不修改当前 230 字节 Payload 上限。每名运动员最多 100 条记录，依次拆成 37、37、26 条三个分片。少于 38 条时只发送一个分片。没有圈记录的运动员不发送 `0x16`。

固件按运动员槽位顺序发送；同一运动员的分片连续发送，并按分片序号递增。分片中的圈号必须严格递增。

### `0x17` 圈历史传输状态

发送方为 STM32，Payload 长度为 1：

```text
byte0 = 0x01：开始传输
byte0 = 0x00：结束传输
```

空历史仍发送开始和结束。若发送任意分片失败，固件使用 `0xF0` 返回触发命令 `0x15` 和现有 LoRa 发送失败状态，并仍尝试发送结束标记，使小程序可以退出接收状态。

新增状态码：

```text
0x10：运动员圈记录已满
```

该状态由有效过线触发，因此 `0xF0` 的原始命令 ID 使用 `0x12`，与现有运动员成绩发送失败路径一致。

## 小程序重连流程

蓝牙连接或自动重连成功后，小程序继续先发送 `0x03` 获取设备状态。若设备处于检测中且本地存在当前比赛会话，则按顺序执行：

```text
0x11 获取当前运动员成绩
等待 0x13 结束
0x15 获取全部圈历史
等待 0x17 结束
校验并一次性更新本地数据
```

`0x11` 返回的当前 `0x12` 快照在同步期间缓存，用来校验每名运动员的最终圈数、最近单圈时长和总时长。`0x16` 分片在 `0x17` 开始和结束之间缓存，不在接收过程中逐条写入本地存储。

接收期间每获得一个合法分片都重新开始 10 秒无数据超时。出现断联、超时、非法长度、未知运动员、重复分片、缺失分片、圈号不连续、超过 100 条，或者历史最后一条与 `0x12` 当前快照不一致时，本次同步失败；小程序丢弃临时缓存、保留同步前的本地数据并显示同步错误。

## 本地成绩重建

固件圈数组只保存单圈时长和圈号，不额外保存总时长。对每名运动员，当前 `0x12` 快照中的总时长减去全部已保存单圈时长之和，得到该运动员圈号 0 时相对统一比赛时钟的初始偏移。随后按圈号累加单圈时长，即可还原每次过线的总时长。

小程序将所有运动员还原出的过线事件按总时长升序排列；相同总时长沿用现有运动员 ID 排序规则。之后从当前比赛参赛名单创建临时计分状态，按顺序重放全部事件，使自动补圈、当前排名和结束圈逻辑继续由现有领域逻辑计算。

只有全部分片与当前快照校验通过后，小程序才：

1. 用重建结果替换当前内存计分状态；
2. 用“运动员 ID + 原始圈号”作为唯一键替换当前比赛的圈成绩列表；
3. 保存最新补圈状态和比赛阶段到当前比赛会话；
4. 刷新实时比赛页和历史成绩页。

重复重连并读取同一份固件历史时，结果保持不变，不产生重复成绩。

## 模块边界

固件侧：

- `DetectionController.h` 负责圈记录写入、容量限制和只读遍历；
- `DetectProtocol.h` 负责新命令常量、状态码、6 字节记录编解码和分片 Payload；
- `LoraManager.h` 负责发送 `0x16`、`0x17` 数据包及新命令长度校验；
- `SpeedSkatingTimer.ino` 负责响应 `0x15` 并遍历运动员分片发送；
- RFID 队列和 8 秒规则保持原职责，不加入协议或历史同步逻辑。

小程序侧：

- 协议模块只负责 `0x16`、`0x17` 的字段解码与格式校验；
- `RaceController` 负责同步顺序、接收状态、超时与提交时机；
- 新建独立的圈历史重建模块，负责分片集合校验、总时长还原和事件排序；
- `ScoreRepository` 提供原子替换当前比赛成绩的方法，不感知蓝牙分片；
- 页面继续订阅现有 store/repository，不新增独立操作按钮。

## 测试与验收

固件自测覆盖：

- 6 字节记录的大端序写入和读取；
- 首次定义不写圈记录，有效过线逐圈追加；
- 8 秒内重复检测不追加；
- 多名运动员分别维护 100 条记录；
- 第 100 条成功，第 101 次不改变当前成绩并返回记录已满；
- 37、38、74、75、100 条记录的分片边界；
- 空历史仍返回开始和结束；
- `0x02` 清空圈记录。

小程序测试覆盖：

- `0x16`、`0x17` 合法和非法 Payload；
- 重连时严格执行 `0x03 -> 0x11 -> 0x15`；
- 多运动员、多分片乱序或缺失时拒绝提交；
- 使用当前快照还原每圈总时长；
- 重放后排名、自动补圈和当前状态正确；
- 重复同步不产生重复成绩；
- 断联或超时保留原本地数据；
- 现有实时 `0x12`、自动重连和后端同步测试保持通过。

完成自动化测试后仍需进行 STM32 与微信小程序实机联调，重点验证满 50 人、每人 100 圈时的传输耗时、LoRa 连续发送稳定性及重连期间的界面反馈。
