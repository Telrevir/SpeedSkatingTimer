# 运动员同步协议框架设计

## 1. 目标

小程序直接切换到新版固件协议，不保留旧版 `0x13` EPC 上报兼容模式。固件负责运动员圈数和总时长，小程序保留本地运动员主档、比赛分组、排名、领滑、结束圈和历史成绩职责。

未在本设计中修改的命令继续沿用当前协议定义，包括 `0x01` 开始检测、`0x02` 停止并重置、`0x03/0x04` 比赛状态和 `0xF0` 通用执行状态。

## 2. 新命令语义

| 命令 | 方向 | Payload | 含义 |
| --- | --- | --- | --- |
| `0x10` | 小程序→固件 | 7 字节 | 定义 EPC 是否为运动员，并携带运动员 ID |
| `0x11` | 小程序→固件 | 0 字节 | 检测中请求全部运动员信息 |
| `0x12` | 固件→小程序 | 6 字节 | 返回运动员 ID、圈数和总时长 |
| `0x13` | 固件→小程序 | 1 字节 | 标记运动员列表传输开始或结束 |
| `0x14` | 固件→小程序 | 4 字节 | 上报尚未定义的普通 EPC |

旧版 `0x13`“EPC + 总时长”语义完全移除。

## 3. 协议编解码

新增 `miniprogram/protocol/athlete-sync-codec.ts`，集中实现新命令 Payload：

```ts
export interface AthleteClassification {
  isAthlete: boolean
  epc: string
  athleteId: number | null
}

export interface FirmwareAthleteScore {
  athleteId: number
  lapCount: number
  totalCentiseconds: number
}

export type AthleteTransferState = 'receiving' | 'idle'
```

`0x10` 编码规则：

```text
byte0：0x01 运动员，0x00 非运动员
byte1-byte4：EPC 原始 4 字节
byte5-byte6：运动员 ID，uint16 大端；非运动员固定填写 0x0000
```

`0x12` 解码规则：

```text
byte0-byte1：运动员 ID，uint16 大端
byte2：圈数，uint8
byte3-byte5：总时长，uint24 大端百分秒
```

`0x13` 解码规则：`0x01` 为 `receiving`，`0x00` 为 `idle`。其他长度或取值无效。

`0x14` 必须正好包含 4 字节 EPC，并转为 8 位大写十六进制文本。

## 4. 前台同步

`RaceController` 新增幂等方法：

```ts
syncForegroundState(): Promise<void>
```

仅当业务连接状态为已连接时执行，并用单个共享 Promise 合并并发调用。同步顺序为：

1. 发送 `0x03`；
2. 等待对应的合法 `0x04`，超时则本轮同步失败；
3. `0x04` 返回检测中时建立列表传输等待并发送 `0x11`；
4. 收到 `0x13 [0x01]` 后确认传输开始，收到随后的 `0x13 [0x00]` 后完成本轮同步；列表传输超时则本轮同步失败；
5. `0x04` 返回已停止时跳过 `0x11`，因为停止操作已经清空固件临时名单。

蓝牙首次连接成功后调用一次。`App.onShow` 在小程序启动或恢复前台时再次调用；未连接时安静跳过。`App.onHide` 只记录进入后台，不尝试维持后台执行。

## 5. 运动员传输状态

控制器保存 `idle | receiving` 两种传输状态：

- 收到 `0x13 [0x01]` 时切换为 `receiving`；
- 收到 `0x13 [0x00]` 时切换为 `idle`；
- 非法长度或未定义值不改变现有状态和成绩。

该状态只用于同步进度、诊断和界面状态，不改变 `0x12` 的处理方式。所有合法 `0x12` 无论在 `idle` 还是 `receiving` 状态下，都通过同一个普通成绩入口立即更新；不建立临时成绩集合，不延迟提交，也不设置列表传输专用成绩分支。

## 6. `0x14` 分类与 `0x10` 定义队列

收到合法 `0x14` 后，控制器使用本地有效 EPC 索引查找运动员，并按本场锁定参赛 ID 判断：

- EPC 未绑定有效运动员：定义为非运动员；
- 未选择比赛分组且 EPC 已绑定：定义为运动员；
- 已选择分组且运动员属于本场锁定名单：定义为运动员；
- 已选择分组但运动员不属于本场锁定名单：定义为非运动员。

“是运动员”时使用本地永久运动员 ID；“非运动员”的 ID 字段固定填写 `0x0000`。

由于 `0xF0` 只包含原命令 ID，不包含 EPC，所有 `0x10` 必须通过独立的 `EpcDefinitionQueue` 串行执行：一次只发送一个 `0x10`，等待它的 `0xF0` 成功或失败后再发送下一项。队列只负责 `0x14 → 0x10 → 0xF0`，不等待、不调用也不修改 `0x12` 成绩处理。

固件容量限制为每场最多 50 名运动员和 50 个非运动员 EPC：

- 开始前参赛名单超过 50 人时阻止开始；
- `0x10` 收到成功 `0xF0` 后，只增加对应类别的成功定义数量；
- `0x10` 失败不增加数量；
- 达到某类别 50 个后，不再发送该类别的新 `0x10`，并记录容量错误；
- 队列中的 EPC 只用于避免同一待处理事件重复入队，成功定义数量不参与成绩计算。

## 7. `0x10` 执行状态与 `0x12` 独立性

`0xF0` 对 `0x10` 返回成功时，定义队列完成当前项并更新容量计数，不提前修改成绩，也不等待后续 `0x12`。

`0xF0` 对 `0x10` 返回失败时：

- 不自动重试同一命令；
- 不增加容量计数；
- 保存最近一次同步错误并通知状态订阅者；
- 下一次前台恢复或重新连接时，通过 `0x11` 全量同步固件成绩。

`0x12` 是独立的固件成绩通道。任何来源的合法 `0x12` 都按普通成绩处理，不检查它是否由某次 `0x10` 触发，也不因任何 `0x10` 成功、失败或等待状态而过滤。

## 8. 固件权威成绩

`LocalRaceScoring` 使用固件成绩入口：

```ts
applyFirmwareScore(
  athleteId: number,
  lapCount: number,
  totalCentiseconds: number,
): LocalAthleteScore | null
```

规则：

- 运动员必须属于当前比赛锁定名单；
- 圈数直接采用固件值，小程序不再自行加一；
- 总时长直接采用固件百分秒值；
- 同一运动员存在上一条成绩且圈数恰好增加 1 时，单圈时间使用总时长差；跨越多圈恢复时不能把多圈总差值显示成单圈时间，因此单圈时间为空；
- 首次恢复成绩没有上一条基准时，单圈时间为空；
- 排名按圈数降序、总时长升序、运动员 ID 升序；
- 排名第一的运动员为领滑运动员；
- 点击结束时捕获领滑运动员当前圈数作为 `finishLap`；
- 其他运动员达到或超过 `finishLap` 后冻结。

未知 ID、归档 ID、非本场参赛 ID 和非法数值不修改现有成绩。

## 9. 本地进行中比赛会话

新增版本化本地存储 `ActiveRaceSessionRepository`，只保存恢复分类和容量控制所需的数据：

```ts
export interface ActiveRaceSession {
  participantIds: number[]
  activeGroupId: string | null
  athleteDefinitionCount: number
  nonAthleteDefinitionCount: number
}
```

生命周期：

- `0x01` 成功后保存开始时锁定的参赛 ID 和分组 ID，两个计数初始化为 0；
- 每个 `0x10` 成功后只持久化对应类别的新计数；
- 小程序冷启动后加载该会话，恢复本场分组判断和容量边界；
- 固件返回检测中时，以会话参赛 ID 恢复本地运行态，再通过 `0x11/0x12` 恢复成绩；
- `0x02` 成功后删除会话；
- 会话不保存成绩、不保存 EPC 集合，也不从 `0x12` 修改两个定义计数。

如果固件处于检测中但本地会话不存在，小程序不能可靠知道尚未被固件定义的参赛运动员范围，保持现有“设备仍在检测，请重置”保护状态，不自动构造比赛。
该保护状态下仍允许 `0x11` 查询用于完成协议同步，但收到 `0x12` 或 `0x14` 时不修改成绩、不发送 `0x10`，并记录“缺少本地比赛会话”诊断。恢复到有效会话时，同时恢复其 `activeGroupId` 对应的当前分组显示。

## 10. 状态错误与协议错误

补充 `0xF0` 状态码：

- `0x0E`：数据包接收超时；
- `0x0F`：RFID 通信错误。

非法 `0x12/0x13/0x14` Payload 被忽略并记录诊断，不覆盖已有成绩。`0x03`、`0x10` 等等待响应的操作各自拥有超时和唯一在途请求，避免一个 `0xF0` 被多个业务操作消费。

## 11. 生命周期和连接边界

本框架不承诺 iOS 后台持续 BLE 收包。恢复前台后只在当前业务连接状态为已连接时执行同步。BLE 物理断开检测和自动重连属于连接恢复层；连接恢复成功后调用同一个 `syncForegroundState()`，不复制协议同步逻辑。

## 12. 测试策略

测试通过现有公开控制器 API、真实编解码函数和内存传输实现验证，不向生产代码增加测试专用入口。

覆盖范围：

- 新命令 ID 和所有新 Payload 向量；
- 首次连接及前台恢复先请求 `0x03`，只在检测中继续发送 `0x11`；
- 未连接时不发送，并发同步被合并；
- `0x13` 只改变传输状态；
- `0x12` 在任何传输状态下走同一更新路径；
- 固件圈数覆盖本地圈数，排名和领滑重新计算；
- `0x14` 对未绑定、无分组、组内和组外 EPC 产生正确 `0x10`；
- 多个 `0x10` 串行等待各自 `0xF0`；
- `0x10` 成功、失败和容量上限不影响 `0x12`；
- 本地进行中会话的创建、计数更新、冷启动加载和重置删除；
- 开始、结束、重置和其他未修改命令保持原行为。

## 13. 本阶段交付边界

本阶段实现完整的新协议编解码、前台同步、定义队列、固件权威成绩、本地会话恢复和自动化测试。BLE 后台常驻不在小程序平台能力范围内；断线期间的成绩通过恢复连接后的 `0x11` 获取当前固件状态。
