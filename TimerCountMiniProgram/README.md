# 轮滑计时微信小程序

这是从 Android `TimerCountApp` 迁移出的原生微信小程序。小程序通过 BT04-E 的 BLE GATT 通道连接计时固件，并按 `LORAProtocol-byte.md` 的二进制帧协议通信。

## 当前功能

- 搜索并连接 `ESP32-LORA-BRIDGE`，校验 `FFE0/FFE2/FFE1` 服务和特征，订阅通知并分片写入。
- 本地维护运动员 ID、姓名、单 EPC、分组、归档状态及历史成绩。
- “开始”发送 `0x01`；“结束”仅锁定领滑当前圈；“重置”发送 `0x02`，成功后清除本场数据。
- `0x14` 上报普通 EPC；小程序按当前比赛分组分类，再以串行 `0x10` 告知固件是否为运动员。
- `0x12` 提供固件权威的运动员 ID、原始圈数、单圈用时和总用时。小程序保留原始值，并仅在高置信度识别到 RFID 漏检时累计补圈偏移；排名、领滑和结束圈使用修正圈数。
- `0x13` 仅表示 `0x11` 名单传输开始/结束，不参与成绩处理。
- 开始比赛后，本地长期保存参赛 ID、分组 ID、运动员/非运动员成功定义数、本地比赛阶段与结束圈，以及每名运动员的补圈偏移和最近真实圈速历史；成功重置后删除。
- 小程序回到前台且蓝牙业务状态为已连接时，先发送 `0x03`。若 `0x04` 表示正在检测，再发送 `0x11` 并等待 `0x13` 完成，以恢复固件当前成绩。

`0x10` 和 `0x12` 是相互独立的流程：`0x10` 的成功或失败不会筛选、等待或改变任何有效 `0x12`。

自动补圈采用保守规则：至少已有两个有效完整单圈、历史波动不超过 15%、固件原始圈数本次只增加 1，且当前间隔可高置信度分摊为 2～3 圈时，单次最多补 2 圈。估算圈不写回真实圈速历史，也不生成虚拟过线或虚拟排名记录；界面以普通色原始圈数和橙色 `+N` 分开显示。

## 导入与运行

1. 执行 `npm install`（或使用项目锁定的 pnpm）。
2. 执行 `npm test` 和 `npm run typecheck`。
3. 在微信开发者工具中导入本目录。
4. 在 `project.config.json` 的 `appid` 字段填写正式小程序 AppID。
5. 使用支持蓝牙的真机验证；开发者工具模拟器无法完整验证 BLE。
6. 用 `AT+UUID`、`AT+CHAR`、`AT+WRITE` 确认 BT04-E 分别为 `FFE0`、`FFE1`、`FFE2`。

## 重要限制

- 微信小程序无法保证 iOS 后台持续运行或持续接收 BLE 通知。恢复前台后的 `0x11` 同步用于取回固件仍保存的当前运动员状态。
- 运动员主档和比赛会话只保存在当前微信客户端；清理存储、删除小程序数据或更换手机可能丢失。
- 扫描添加、导入导出、云同步、多 EPC 和测试专用界面尚未实现。
- 每场最多 50 名运动员，并分别最多成功定义 50 个运动员 EPC 和 50 个非运动员 EPC。
- 自动补圈是小程序侧估算补偿，不代表精确过线时间；正式使用前仍需用真实比赛数据校准阈值并完成裁判验收。

## 目录

- `miniprogram/protocol`：帧协议和字段编解码。
- `miniprogram/transport`：微信 BLE API 适配与分片传输。
- `miniprogram/services`：运动员目录、比赛控制、同步队列和成绩记录。
- `miniprogram/stores`：页面可订阅状态。
- `miniprogram/pages`：比赛、排名、运动员和历史成绩页面。
- `tests`：Node.js 单元及控制器集成测试。

协议实现已经通过自动化测试和 TypeScript 类型检查；仍需在更新后的固件、微信开发者工具及 Android/iOS 真机上完成端到端验收。
